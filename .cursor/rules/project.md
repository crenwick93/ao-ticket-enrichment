# AO Ticket Enrichment — Project Rules

## What This Project Is

An AO (Automation Orchestrator) demo that enriches ServiceNow incidents with AI-driven root cause analysis. An nginx EC2 instance is monitored by Prometheus + AlertManager. When nginx fails, a webhook bridge creates a ServiceNow incident, EDA detects it, and triggers an AO workflow that gathers diagnostics, runs AI analysis, and updates the ticket.

There are **two AO workflows**:
1. **Enrichment only** (`ao/ticket-enrichment.json`) — Diagnostics → AI RCA → Update SNOW
2. **Enrichment + Remediation** (`ao/ticket-enrichment-remediation.json`) — Same plus AI searches AAP for a fix job template and runs it

## Related Projects

This project was adapted from `../ansible-lightspeed-ticket-enrichment/` (ALIA version) and follows patterns from `../ao-cve-remediation-scalable/` (CVE project). When in doubt, reference the CVE project for AO workflow JSON format, CaC structure, and coding patterns.

## Key Technical Decisions

### Environment Variables
- ServiceNow vars support both `SERVICENOW_*` and `SN_*` naming (apply.yml has fallback lookups)
- `MONITORING_HOST_IP` must exist in `.env` for break/fix scripts to work
- AO webhook credentials (`AO_WEBHOOK_PATH`, `AO_WEBHOOK_CLIENT_ID`, `AO_WEBHOOK_CLIENT_SECRET`) come from AO after publishing the workflow

### ServiceNow PDI Specifics
- `close_code` must be `"Solution provided"` (not `"Solved (Permanently)"` — confirmed via API)
- Resolving an incident is a two-step operation: add work notes first, then resolve (single call gets rejected)
- Work notes must be wrapped in `[code]...[/code]` tags for HTML rendering
- AI output uses HTML formatting (`<h3>`, `<p>`, `<ul>`, `<code>`, `<pre style="white-space: pre-wrap;">`)

### AO Workflow JSON Format
- Uses `schema_version: "2.0.0"`, `triggers` array, `edges` array, `${var}` syntax
- Node types: `aap_job_template`, `agentic`, `switch`
- AAP job nodes use `parameters.job_template_name` and `parameters.extra_vars`
- Agentic nodes use `parameters.prompt` and `parameters.model`
- AI output is at `${node.result.content.field}` when using response schema
- Switch conditions: `${node.result.content.field} == 'value'`

### EDA
- The EDA activation must NOT have event streams attached — it uses `servicenow.itsm.records` source from the rulebook
- The EDA controller credential needs host URL with `/api/controller/` path suffix (AAP 2.5+)
- The `webhook_path` is passed from EDA activation extra_vars → rulebook → bridge job → AO trigger
- EDA activation can't be updated by CaC while running — disable/re-enable in AAP UI

### CaC
- CaC cannot overwrite encrypted credential fields that already exist — delete the credential first or edit in AAP UI
- The controller project must be synced in AAP before CaC can create job templates referencing its playbooks
- The EDA project must also be synced separately for rulebook activations
- Uses `set -a; source .env; set +a` pattern for loading env vars (not `export $(grep | xargs)`)

### Infrastructure
- Terraform provisions EC2 + VPC + Elastic IP in eu-west-1
- SSH key is generated by Terraform at `setup/terraform/demo-key.pem`
- The webhook bridge templates in `monitoring_host_ip` (from `ansible_host`) into incident descriptions as "Affected host IP: <ip>"
- The `gather_diagnostics.yml` playbook extracts the target host IP from the incident description

## Scripts
- `./scripts/break-nginx.sh` — injects `unknown_directive broken;` into nginx.conf
- `./scripts/fix-nginx.sh` — removes it and restarts
- `./setup/scripts/setup-apply.sh` — deploys the full monitoring stack
- `./ansible_deployment/scripts/cac-apply.sh` — applies all AAP/EDA objects

## Deployment Order
1. `terraform apply` (provisions EC2)
2. `setup-apply.sh` (installs nginx + monitoring + webhook bridge)
3. `cac-apply.sh` (creates AAP objects — needs project synced first)
4. Import AO workflow in AO UI, configure agentic nodes, publish
5. Update `.env` with AO webhook creds, re-run `cac-apply.sh`
6. Restart EDA activation in AAP UI
